[14] (Heading 1) Introducción
[15] (normal) El presente trabajo sobre el diseño e implementación del Módulo de Investigación en la Universidad de San Buenaventura Medellín ha sido preparado como parte de la estrategia de gestión y centralización de proyectos académicos. Este documento ofrece una visión general del software propuesto para estructurar, hacer seguimiento y administrar de manera efectiva las entregas, formatos y tablas del proceso investigativo institucional.
[16] (normal) El proyecto responde a la necesidad de sistematizar los procesos de investigación, facilitando el control de las entregas y la organización de la información base. Se propone un enfoque basado en la digitalización y estandarización del módulo actual, permitiendo desarrollar herramientas y plataformas para la recolección, validación y análisis objetivo de los proyectos de investigación.
[17] (normal) Este documento detalla el proceso de transformación digital del Módulo de Investigación, delineando las fases esenciales para su implementación y proporcionando una visión global del proyecto. La estructura contempla la identificación de roles, la definición de actividades clave y la generación de artefactos necesarios para asegurar una gestión rigurosa y precisa, contribuyendo a la mejora continua y al cumplimiento de los estándares de calidad institucional.
[18] (Heading 2) Propósito
[19] (normal) El propósito del Plan de Desarrollo de Software es establecer un punto de partida claro para la construcción del software, proporcionando la información necesaria para la gestión y control del proyecto, y describiendo el enfoque que se adoptará para el desarrollo del software. Los usuarios del Plan de Desarrollo del Software son:
[20] (normal) El jefe del proyecto: lo utiliza para organizar la agenda y necesidades de recursos, y para realizar su seguimiento.
[21] (normal) Los miembros del equipo de desarrollo: lo usan para entender lo que deben hacer, cuándo deben hacerlo y qué otras actividades dependen de ello.
[22] (normal) Los compañeros del semillero o personas interesadas: utilizarán este documento como una herramienta para conocer de primera mano y de manera eficaz los pormenores del proyecto. Además, en algunos casos, podrá servir como referencia para futuros cambios o implementaciones en sus propios proyectos.
[24] (Heading 2) Alcance
[25] (normal) El Plan de Desarrollo del Software describe que el proyecto abarca el diseño e implementación del Módulo de Investigación en la Universidad de San Buenaventura Medellín. Este sistema digital permitirá gestionar, estructurar y hacer seguimiento integral a los proyectos de investigación académica, incluyendo sus tablas de datos, entregas de avance y plantillas base. El desarrollo se realizará por iteraciones, elaborando documentos llamados entregables, así como un producto de software que cumplirá con los requisitos funcionales y no funcionales. El proyecto comprenderá la captura de requisitos mediante consultas con las partes interesadas, el desarrollo de una documentación de visión preliminar y la planificación de iteraciones para la implementación del sistema. Durante el proceso, se desarrollarán herramientas y plataformas que faciliten una gestión transparente y organizada de la investigación, garantizando la calidad y conformidad con los estándares institucionales.

[85] (normal) Historias de usuario
[86] (normal) Las historias de usuario son descripciones breves y simples de una funcionalidad deseada del sistema, escritas desde la perspectiva del usuario final. Su propósito es capturar lo que el usuario quiere lograr con el software y generalmente siguen un formato específico: "Como [tipo de usuario], quiero [acción] para [beneficio/valor]." Estas descripciones informales son esenciales en metodologías ágiles como Scrum, ayudando a definir y priorizar las tareas de desarrollo, y se utilizan para capturar los requisitos del usuario y comunicar las necesidades del software a los equipos de desarrollo.
[87] (normal) Las historias de usuario suelen seguir una estructura sencilla: Como [rol del usuario], quiero [acción deseada], para lograr [beneficio]. Por ejemplo, una historia de usuario para un sitio web de comercio electrónico podría ser: Como cliente, quiero poder buscar productos por categoría, para poder encontrar fácilmente los productos que busco.

[94] (normal) Una historia de usuario bien escrita debe contener los siguientes elementos:
[96] (normal) Rol del usuario: El tipo de usuario que realizará la acción.
[97] (normal) Acción deseada: La acción que el usuario quiere realizar.
[98] (normal) Beneficio: El beneficio que el usuario obtendrá al realizar la acción.
[100] (normal) Además de estos elementos esenciales, las historias de usuario pueden incluir información adicional, como:
[102] (normal) Criterios de aceptación: Los criterios deben cumplirse para que la historia se considere completa.
[103] (normal) Prioridad: La importancia de la historia para el usuario y el negocio.
[104] (normal) Estimación del esfuerzo: El tiempo y el esfuerzo que se estima que llevará implementar la historia.

[124] (normal) Requisitos no funcionales
[125] (normal) Un requisito no funcional o atributo de calidad es, en la ingeniería de sistemas y la ingeniería de software, un requisito que especifica criterios que pueden usarse para juzgar la operación de un sistema en lugar de sus comportamientos específicos, ya que estos corresponden a los requisitos funcionales.
[127] (normal) Los requisitos no funcionales de software (RNFS), también conocidos como requisitos de calidad o atributos del sistema, son características y criterios que describen cómo debe ser el rendimiento, la seguridad, la usabilidad y otros aspectos de un sistema o software más allá de su funcionalidad básica. Estos requisitos son esenciales para garantizar que el software sea de alta calidad y satisfaga las necesidades de los usuarios.
[129] (normal) ¿Por qué son importantes los requisitos no funcionales?
[131] (normal) Los RNFS son importantes por varias razones:
[133] (normal) Garantizan la calidad del software: Ayudan a asegurar que el software sea confiable, seguro, usable y eficiente.
[134] (normal) Satisfacen las necesidades del usuario: Aseguran que el software cumpla con las expectativas de los usuarios.
[135] (normal) Reducen los costos: Ayudan a identificar y prevenir problemas antes de que se conviertan en costosos errores.
[136] (normal) Mejoran la competitividad: Un software que cumple con los RNFS es más competitivo en el mercado.
[138] (normal) ¿Cuáles son los tipos de requisitos no funcionales?
[140] (normal) Existen muchos tipos de RNFS, pero algunos de los más comunes son:
[142] (normal) Rendimiento: El software debe ser rápido, receptivo y eficiente.
[143] (normal) Seguridad: El software debe protegerse contra accesos no autorizados, datos corruptos y otras amenazas.
[144] (normal) Usabilidad: El software debe ser fácil de usar, aprender y entender.
[145] (normal) Escalabilidad: El software debe poder adaptarse a un mayor número de usuarios o datos.
[146] (normal) Mantenibilidad: El software debe ser fácil de modificar y actualizar.
[147] (normal) Portabilidad: El software debe poder ejecutarse en diferentes plataformas o dispositivos.
[148] (normal) Confiabilidad: El software debe ser confiable y funcionar sin errores.
[149] (normal) Disponibilidad: El software debe estar disponible para los usuarios cuando lo necesiten.
[151] (normal) ¿Cómo se definen los requisitos no funcionales?
[152] (normal) Los RNFS se definen típicamente durante la fase de recopilación de requisitos del proceso de desarrollo de software. Esto implica entrevistar a los usuarios, analizar los casos de uso y consultar con otras partes interesadas.
[154] (normal) Los RNFS deben ser medibles y verificables, para que se pueda evaluar si el software cumple con ellos. Por ejemplo, un requisito no funcional de rendimiento podría especificar que el software debe cargarse en menos de dos segundos.
[156] (normal) ¿Cómo se implementan los requisitos no funcionales?
[158] (normal) Los RNFS se implementan a lo largo del proceso de desarrollo de software. Los desarrolladores deben tener en cuenta los RNFS al diseñar, codificar y probar el software.
[160] (normal) Herramientas y técnicas para la gestión de requisitos no funcionales. Existen varias herramientas y técnicas que pueden ayudar a gestionar los RNFS, como:
[162] (normal) Documentos de requisitos no funcionales: Estos documentos describen los RNFS para el sistema o software.
[163] (normal) Herramientas de modelado: Estas herramientas pueden utilizarse para crear modelos de los RNFS.
[164] (normal) Herramientas de análisis: Estas herramientas pueden utilizarse para analizar los RNFS e identificar posibles problemas.
[165] (normal) Herramientas de seguimiento: Estas herramientas pueden utilizarse para realizar un seguimiento del progreso de la implementación de los RNFS.

[206] (normal) Plan de despliegue
[207] (normal) Los planes de despliegue definen los segmentos y las tareas relacionadas con los segmentos que dirigen los despliegues. Las fases en un reléase se derivan del ciclo de vida. Los segmentos de una fase se derivan del plan de despliegue. Cuando crea un despliegue, selecciona un plan de despliegue de los planes asociados al Release. El plan que elija determina los segmentos y las tareas inicialmente disponibles para el despliegue. Puede añadir o suprimir segmentos y tareas incluso después de que el despliegue se haya iniciado. Los cambios que realice a un plan durante un despliegue pasan a formar parte del plan en sí mismo. También puede trabajar directamente en un plan de despliegue fuera de cualquier despliegue.

[222] (normal) Manual de instalación:
[223] (normal) Un manual de instalación de software es una guía detallada que describe cómo instalar un programa de software en un ordenador. Está escrito en un lenguaje sencillo y ofrece instrucciones paso a paso para completar el proceso de instalación.
[224] (normal) El objetivo principal de un manual de instalación de software es ayudar a los usuarios a instalar el software correctamente y sin problemas.
[225] (normal) Los manuales de instalación de software suelen incluir información sobre:
[227] (normal) Preparación para la instalación:
[228] (normal) Requisitos del sistema: El software necesita un determinado conjunto de hardware y software para funcionar correctamente. El manual de instalación debe enumerar los requisitos del sistema para que los usuarios puedan asegurarse de que su ordenador cumple con ellos antes de empezar la instalación.
[229] (normal) Descarga del software: El software suele descargarse desde Internet o desde un dispositivo externo. El manual de instalación debe proporcionar instrucciones sobre cómo descargar el software.
[230] (normal) Desinstalación de software anterior: Si ya está instalado un software similar en el ordenador, puede que desinstalarse antes de instalarlo. El manual de instalación debe proporcionar instrucciones sobre cómo desinstalar el software anterior.
[232] (normal) Proceso de instalación:
[234] (normal) Ejecución del programa de instalación: Una vez descargado el software, hay que ejecutar el programa de instalación. El manual de instalación debe proporcionar instrucciones sobre cómo hacerlo.
[235] (normal) Selección de opciones de instalación: El programa de instalación suele ofrecer varias opciones de instalación. El manual de instalación debe explicar las diferentes opciones y cómo seleccionar la mejor para el usuario.
[236] (normal) Introducción de información: El programa de instalación puede solicitar al usuario que introduzca información, como una clave de licencia o un nombre de usuario y contraseña. El manual de instalación debe proporcionar instrucciones sobre cómo introducir esta información.
[237] (normal) Finalización de la instalación: Una vez completadas todas las opciones de instalación, el programa de instalación finalizará el proceso. El manual de instalación debe proporcionar instrucciones sobre cómo finalizar la instalación.
[239] (normal) Verificación de la instalación:
[241] (normal) Inicio del software: Una vez finalizada la instalación, el usuario debería poder iniciar el software. El manual de instalación debe proporcionar instrucciones sobre cómo hacerlo.
[242] (normal) Prueba del software: El usuario debe probar el software para asegurarse de que funciona correctamente. El manual de instalación puede proporcionar instrucciones sobre cómo probar el software.
[243] (normal) Solución de problemas: Si el usuario encuentra algún problema durante la instalación o el uso del software, el manual de instalación debe proporcionar instrucciones sobre cómo solucionarlo.

[248] (normal) Actividades :
[250] (normal) Asesorías y sprint Review:
[251] (normal) Asesorías: Son sesiones en las que el equipo de desarrollo recibe orientación y apoyo de expertos. Estas reuniones pueden realizarse en cualquier momento del Sprint y están diseñadas para resolver dudas, recibir feedback temprano y asegurar que el trabajo del equipo esté alineado con las expectativas del proyecto. Las asesorías son esenciales para mantener la calidad y dirección del trabajo, ayudando al equipo a tomar decisiones informadas y evitar posibles desviaciones.
[253] (normal) Sprint Review: Es una reunión que se lleva a cabo al final de cada Sprint. Durante la Sprint Review, el equipo presenta el incremento del producto que han desarrollado a los interesados y stakeholders. Se discuten los avances logrados, se recibe retroalimentación y se establecen los próximos pasos. Esta reunión es crucial para evaluar el progreso del proyecto, ajustar la dirección según las necesidades del cliente, y asegurar que el equipo sigue en el camino correcto hacia el cumplimiento de los objetivos del producto.
[255] (normal) Estudiar temas:
[256] (normal) Implica dedicar tiempo y esfuerzo para profundizar en ciertos temas o áreas de conocimiento. Es un proceso que puede incluir la lectura de materiales, la investigación, la toma de apuntes y la discusión con otros para comprender mejor el contenido. Estudiar temas es clave para adquirir nuevas habilidades, reforzar conocimientos previos y prepararse para aplicaciones prácticas en un proyecto o tarea específica.
[258] (normal) Weekly scrum:
[259] (normal) El Weekly Scrum es una reunión semanal breve en la que el equipo se reúne para revisar el progreso de la semana, discutir cualquier obstáculo que haya surgido y planificar las tareas para la semana siguiente. Es un momento clave para asegurarse de que todos estén en la misma página, ajustar planes según sea necesario y mantener el enfoque en los objetivos del proyecto. Esta reunión ayuda a alinear esfuerzos, resolver problemas de manera oportuna y garantizar que el equipo continúe avanzando de manera efectiva.
[262] (normal) Sprint Retrospective:
[263] (normal) La Sprint Retrospective es una reunión del equipo Scrum donde se reflexiona sobre el Sprint que acaba de terminar. Es un espacio para que el equipo hable sobre lo que salió bien, lo que podría haberse hecho mejor, y para identificar áreas de mejora para el próximo Sprint. Es una oportunidad para aprender, ajustar y seguir mejorando en cada ciclo de trabajo.
[265] (normal) Sprint Goal:
[266] (normal) El Sprint Goal es la meta principal que el equipo se propone alcanzar al final del Sprint. Es una declaración sencilla pero poderosa que define lo que se quiere lograr y mantiene a todos enfocados en la misma dirección. Es como una brújula que guía las decisiones diarias y asegura que el equipo se mantenga alineado con el propósito del Sprint. Al final, es la referencia para evaluar si el Sprint fue un éxito o no.

[282] (Heading 2) Estimaciones del Proyecto
[283] (normal) El proyecto adopta la metodología SDD (Spec-Driven Development) junto con la estructura de Spec Kit. A diferencia de los enfoques tradicionales o ágiles basados en código iterativo (como Scrum), SDD invierte la prioridad: la especificación es la fuente primaria de verdad y el código es únicamente su implementación. Primero se define exactamente QUÉ construir, CÓMO y con qué criterios de aceptación medibles, y posteriormente se procede a la codificación (ejecutada directamente por el equipo o asistida por Inteligencia Artificial).
[284] (normal) Las características fundamentales de esta gestión son:
[285] (normal) Especificación previa a la implementación: Ninguna línea de código se escribe sin estar respaldada por un documento del Spec Kit.
[286] (normal) Gobernanza por Versiones: El proyecto se organiza en versiones cerradas (v1, v2, etc.). Una versión cerrada y etiquetada (tag) no se reabre; los ajustes van a la siguiente versión.
[287] (normal) Autocontención: El conjunto de documentos del Spec Kit contiene la información suficiente para construir o reconstruir la versión desde cero.
[288] (normal) Criterios de Aceptación Medibles y Verificables: Todo requisito o endpoint cuenta con criterios explícitos de aprobación pasibles de prueba (p. ej. mediante smoke tests o respuestas HTTP exactas).

[306] (normal) iii. Reglas de Juego del Proceso
[308] (normal) La Spec manda sobre el código: Si el código ejecuta una función no especificada en el Spec Kit, sobra. Si la Spec define un requisito no presente en el código, está incompleto.
[309] (normal) Principio YAGNI (You Aren't Gonna Need It): Ninguna versión construye o anticipa componentes de versiones futuras. Cada versión limita su desarrollo estricto a su especificación correspondiente.
[310] (normal) Cierre Inmutable: Una vez etiquetada una versión (tag), no se realizan modificaciones directas sobre ella. Cualquier corrección o ajuste pasa a ser "deuda de spec" y se resuelve en la especificación de la siguiente versión.
[311] (normal) Autocontención: El Spec Kit debe permitir reconstruir el software completo sin requerir revisión del código previo ni explicaciones verbales.
[312] (normal) iv. Seguimiento y Control del Proyecto
[313] (normal) Seguimiento de Tareas: Se realiza mediante el documento 8_tasks.md, donde el estado de cada tarea y fase es auditado contra comandos de verificación. No se avanza a una fase siguiente si existen tareas en estado no verificado (en rojo).
[314] (normal) Control de Cambios: Cualquier modificación técnica o funcional debe reflejarse primero en la documentación del Spec Kit correspondiente (documento 4_research.md para decisiones o 2_spec.md para requisitos) antes de modificar el código fuente.
[315] (normal) Control de Calidad: La calidad del sistema se garantiza al validar con 7_quickstart.md que las respuestas HTTP, el comportamiento de base de datos y los criterios de aceptación coincidan de manera exacta con los contratos expuestos en 6_contracts.md.
